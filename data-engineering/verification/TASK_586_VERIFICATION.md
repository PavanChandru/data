# Task #586 – Synthetic Data Verification

## Overview

As part of Task #586, I tested the request archival and lookup join logic using the synthetic data generated by volunteers in PR #161.

The goal was to check whether request records are preserved when joined with lookup tables, whether the readable labels are populated correctly, and how the process handles missing or invalid references.

Since live database access was not available for this test, I used the volunteer-generated mock data and followed the database relationships.

## Test Data

- Users: 5,000
- Requests: 20,000
- Source: Volunteer-generated mock dataset from PR #161
- Test script: `test_synthetic_archive.py`

## Test Data Organization

The test uses volunteer-generated mock data from PR #161.

To make the verification script self-contained, the required CSV files are included under `verification/test_data/`:

- `mock_db/request.csv`
- `mock_db/users.csv`
- `lookup_tables/request_for.csv`
- `lookup_tables/request_isleadvol.csv`
- `lookup_tables/help_categories.csv`
- `lookup_tables/request_type.csv`
- `lookup_tables/request_priority.csv`
- `lookup_tables/request_status.csv`

The test script reads these files using paths relative to its own location. No separate download of PR #161's dataset is required to run the tests.

## What I Tested

I ran the following checks:

1. **Source data validation:** Checked that the request and user datasets were not empty and that their IDs were unique.
2. **Foreign key validation:** Checked the request references against the user and six lookup datasets.
3. **Lookup joins:** Performed LEFT JOINs with request_for, request_isleadvol, categories, request types, priorities, and statuses.
4. **Record preservation:** Checked that all 20,000 requests remained in the output after the joins.
5. **Readable labels:** Verified that the six lookup labels were populated for the valid synthetic records.
6. **Missing references:** Tested NULL and unmatched references for each of the six lookup tables to confirm that the request records were retained.
7. **Duplicate detection:** Checked whether duplicate request IDs and duplicate lookup keys could be detected.
8. **Repeated export:** Serialized the same output twice and confirmed that both results were identical.
9. **Timestamp validation:** Checked that the available timestamp columns could be parsed without errors.

## Results

All 43 checks passed.

| Metric | Result |
|---|---:|
| Total checks | 43 |
| Passed | 43 |
| Failed | 0 |
| Requests in source data | 20,000 |
| Requests in archived output | 20,000 |
| Users | 5,000 |
| Execution time | 0.64 seconds |

All six lookup joins preserved the original request count. The tests for NULL and unmatched references also passed, meaning requests were not dropped when a lookup reference was missing or invalid.

The duplicate detection checks also worked as expected.

## Pending Verification

This test was performed using synthetic data, not the live database or the deployed Lambda function. The volunteer dataset also uses an older request CSV structure and does not cover every column and relationship in the current database schema.

The following checks still need to be completed with access to the actual database and archival process:

- Compare the source database row count with the corresponding S3 archive for the same time window.
- Check for duplicate records and missing records across multiple archive runs.
- Verify that rerunning the Lambda for the same time window does not create duplicate S3 output.
- Test timestamp and watermark handling with a non-UTC database session.
- Check broken references against actual database records.
- Measure the end-to-end execution time of the archival process.

The repeated export test in this work only confirms that the same synthetic data produces identical serialized output. It does not verify that the actual Lambda or S3 process is idempotent.

## Conclusion

The synthetic tests passed all 43 checks. They provide a useful initial validation of the lookup joins, record preservation, and handling of missing or invalid references.

The remaining production-level checks will need to be performed once access to the live database and deployed archival Lambda is available.
